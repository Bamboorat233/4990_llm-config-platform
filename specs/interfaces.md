## 1. Field paths

A **field path** is a dot-separated string naming exactly one editable leaf of a configuration record. It is the single identifier used for three things:

1. binding a form widget: `field_widgets["b.pad_token"]`;
2. reporting a validation problem: `ValidationIssue.field`;
3. locating the value in the stored JSON: `payload["b"]["pad_token"]`.

### Grammar

```
path       := component ( "." segment )*
component  := "a" | "b" | "c" | "d" | "e" | "f" | "g" | "h" | "p"
segment    := JSON object key, verbatim
```

### Rules

1. The first segment is always a component letter defined in `specs/parameters.md` §3–§11. `a`–`g` are the seven execution components, `h` is the optional-arguments bucket, `p` is the prompt section.
2. Every following segment is the **exact key used in the stored JSON** (`specs/parameters.md` §13). No renaming, no camelCase, no abbreviations.
3. Nested models keep their intermediate key: `d.lora.r`, `d.sft.load_best_model_at_end`.
4. Component `h` adds the target stage before the argument name:
   `h.<stage>.<argument>` with `stage ∈ {load_model, load_tokenizer, encode, generate}`, e.g. `h.generate.top_k`.
5. Component `p` holds the prompt fields: `p.system_prompt`, `p.user_prompt_template`, `p.assistant_prompt`, `p.chat_template_override`, `p.verdict_parse_marker`.
6. List-valued fields are addressed as the list itself; individual elements are not addressable: `d.lora.target_modules`, `c.label_values`.
7. Top-level record fields are addressed by their bare key, without a component prefix: `task_type`, `model_id`, `run_status`, `created_by`, `notes`.
8. A path must resolve in the payload produced by `defaults_for()`. A path that does not resolve is a bug in the module that emitted it.

### Examples

| Path | Meaning | JSON location |
| --- | --- | --- |
| `b.pad_token` | tokenizer pad token | `payload["b"]["pad_token"]` |
| `d.sft.load_best_model_at_end` | SFT trainer flag | `payload["d"]["sft"]["load_best_model_at_end"]` |
| `f.temperature` | sampling temperature | `payload["f"]["temperature"]` |
| `h.generate.top_k` | extra `generate()` argument | `payload["h"]["generate"]["top_k"]` |
| `p.system_prompt` | system prompt | `payload["p"]["system_prompt"]` |
| `task_type` | top-level record field | `payload["task_type"]` |

## 2. `defaults_for(model_id, task_type)` return shape

```python
def defaults_for(model_id: str, task_type: Literal["fine_tune", "inference"]) -> dict: ...
```

Returns a **plain `dict`** (not a Pydantic model) that pre-fills the form.

### Top-level keys

Exactly these twelve keys, no more, no fewer:

```
model_id, task_type, run_status,
a, b, c, d, e, f, g, h, p
```

Identity and bookkeeping fields are **not** included:

| Omitted key | Where it comes from |
| --- | --- |
| `config_id` | generated by `ConfigRecord` (UUID4) |
| `config_hash` | computed by `config_fingerprint()` when saving |
| `created_at` | generated by `ConfigRecord` (UTC, ISO 8601) |
| `created_by`, `notes` | `None` until the user fills them in |

Consequence: `ConfigRecord(**defaults_for(model_id, task_type))` is valid. `ConfigRecord` supplies the five omitted fields through default factories (#3).

### Rules

1. Every nested dict contains **every** field of its section, in the spelling of `specs/parameters.md` §3–§11, so the result can be serialised straight to the §13 JSON shape.
2. Each call returns **fresh objects**. Mutating a returned list or dict must never affect a later call.
3. `h` defaults to `{}`.
4. An unknown `model_id` or `task_type` raises `ValueError` naming the accepted values.
5. Values come from `specs/parameters.md` §14 (pre-filled form values), with two clarifications:
   - `f.batch_size` is `1` for both task types. §14 says 2 for fine-tuning, but §13 — the acceptance target of #2 — shows 1, and `f.batch_size` is a generation-time knob that fine-tuning never reads. Treat §14's value as a documentation slip and raise it in review if the research side disagrees.
   - `e.max_length` and `c.max_seq_length` pre-fill to `4096` (the runnable payload of §13). The §5/§7 default column leaves them `null`; `null` remains valid input, it just does not pre-fill a runnable config.

## 3. `ValidationIssue`

```python
class ValidationIssue(TypedDict):
    field: str                                  # a field path from contract 1
    level: Literal["error", "warning"]
    msg: str                                    # one-sentence, user-facing English
```

```python
def validate_cross_fields(cfg: ConfigRecord) -> list[ValidationIssue]: ...
```

### Rules

1. `field` follows contract 1 exactly; it must resolve in the payload.
2. `level` is exactly `"error"` or `"warning"`. Anything else is a bug.
3. `msg` is English, one sentence, names the offending value and the fix; it is shown verbatim in the UI.
4. Validation **returns** issues; it never raises for a validation failure.
5. An empty list means the config passes.
6. At least one `error` blocks saving; `warning` never blocks. Rule 9 (§12 of `specs/parameters.md`) reports `error`, rule 10 reports `warning`.
7. The UI highlights `issue["field"]` and lists every issue in the right-hand panel: red for `error`, yellow for `warning`.
8. A rule that involves two fields reports the path of the field the user should edit. For example, a temperature/`do_sample` mismatch reports `f.do_sample`, because that is the value the rule flips.

### Example

```python
[
    {
        "field": "b.pad_token",
        "level": "error",
        "msg": "Mistral does not have the token '<myPadToken>'; use '<pad>' (id 11) or '</s>'.",
    },
    {
        "field": "p.system_prompt",
        "level": "warning",
        "msg": "DeepSeek concatenates the system prompt right after BOS with no separator; prefer putting the instruction in the user prompt.",
    },
]
```
